# NAL READ BUILD32 — 첫 기수 준비, 개인정보 권리 요청의 실제 접수 구조

## 이번 단계의 실제 설치
첫 기수 `TREND 2027`의 확정 원고 1종, 참가자 시작 안내 1종, 4주 진행 대본은 기존 소스를 그대로 기준으로 정리했습니다. 새 도서 인용·출처 없는 책 요약을 만들지 않았습니다.

기존 저장 파일을 직접 살펴본 기준은 DAY 0 포함 29개 DAY, 총 147개 STEP, 4주 구성입니다. 첫 번째 기수의 모집 날짜·90분 LIVE 실제 시각·Zoom 주소·정원·판매 방식·가격·책 제공 여부·운영자 계정은 아직 확정되지 않았습니다. `integration/nal-read/build32/first-season-operator-packet.json`에서 이를 모두 `null` 또는 `missing`으로 두었으며, **DB의 실제 첫 기수를 만들거나 원고를 공개하지 않았습니다.**

운영 순서는 기존 owner/운영자 신원 확인 → 읽을 책·출처 검토 → 원고 초안 저장 → owner 검토/승인 → 참가 안내 초안 저장/별도 공개 → 4회 LIVE 실제 일정 연결 → 상품/신청약관/정원 결정 → 별도 판매 준비 검증입니다. 이 문서는 입력용 체크포인트이고 실제 서버 작업을 대신하지 않습니다.

## 개인정보 처리에 대한 확인된 위험
개인정보 보호법 제21조는 불필요해진 개인정보의 파기와 다른 법령상 보존이 필요한 경우의 분리 관리를 요구합니다. 전자상거래법 시행령 제6조가 적용되는 소비자 기록은 계약·청약철회 및 결제·공급 기록의 보존기간이 통상 5년, 소비자 불만·분쟁 처리 기록은 3년, 표시·광고 기록은 6개월로 구분됩니다. **이 법정 기록을 모든 코칭 일지에 그대로 5년 보존한다는 의미가 아닙니다.** 적용 여부·기산 시점·고객 고지·자료 보관 정책은 실제 영업 형태를 기준으로 최종 확인해야 합니다.

기존 데이터 모델에는 `nal_private.read_experiments.source_snapshot`과 `nal_private.read_report_editions.snapshot`처럼 **원 답변을 복제해 보관하는 필드**가 있습니다. `source_answer_id`가 ON DELETE SET NULL로 바뀌어도 사본 문자열은 남습니다. 따라서 답변 한 행만 지우고 '개인 기록 삭제 완료'라고 표시하면 안 됩니다. 전체 삭제는 원 기록·파생 사본·리포트·개인 메모·캐시/백업에 대한 별도의 파기 실행 경계가 필요합니다.

## 이번에 구현·설치한 요청 접수 경계
`nal_private.read_privacy_requests`는 범위를 `read-journal`(셀프코칭 개인 기록)과 `account-closure-review`(탈퇴·보존 분리 검토)로 구분합니다. 본인 확인을 거친 서버 역할만 다음을 호출할 수 있습니다.

- `inventory`: 내 답변·초안·실험·리포트·준비 체크·LIVE 메모의 **건수**만 조회합니다. 실제 답변 문장이나 주문 내용을 반환하지 않습니다.
- `request`: 동일 요청 ID의 재전송을 중복 접수하지 않고, 접수/범위를 기록합니다. 명시적 확인이 필요합니다.
- `status`: 본인 요청 기록과 접수 상태만 조회합니다.
- `withdraw`: 검토 전 `requested` 상태인 본인의 요청만 철회합니다.

접수 테이블은 RLS가 켜져 있고 익명·로그인 브라우저 역할에는 직접 권한이 없습니다. DB 함수는 SECURITY INVOKER이며 service_role 이외 실행을 허용하지 않습니다. 이 기능은 개인 기록 삭제·Auth 탈퇴·계약 기록 분리보관을 **실행하지 않습니다**. 담당자 삭제 심사·데이터 파기 실행·법정 보존 처리는 차기 별도 단계입니다.

기존 `nal-account`의 소스에는 `privacy` 경로를 같은 로그인 검증을 사용하도록 연결하되 `NAL_PRIVACY_REQUEST_ENABLED` 플래그 **기본 OFF**를 추가했습니다. 기존 `NAL_ACCOUNT_ENABLED`도 그대로 유지합니다. 이 신규 경로의 서버 배포/운영 활성화 여부는 BUILD32 결과 이력에서 별도로 구분합니다. 화면 노출이나 개인정보 요청 접수 성공을 주장하지 않습니다.

## 운영 개인정보처리방침의 정정 필요
현재 `nal/policy/privacy/` 안내에는 '개인정보 수집 기능 연결 전'이라는 초기 정적 문구가 남아 있습니다. 실제 계정/코칭 기록을 고객에게 받기 전에는 처리 주체, 연락처, 수집 정보, 보유 기간, 위탁·국외 이전, 삭제 요청과 법정 보존 구분, 백업·로그 파기 절차를 실제 운영 조건에 맞게 갱신해야 합니다. 주체·연락처·정책 승인자와 정확한 보존기간은 지금 임의로 만들어 넣지 않았습니다. BUILD32는 기존 공개 정책 페이지를 수정하지 않습니다.

## 구현 범위와 미완료
- 실제 DB에 privacy request intake 구조만 설치하며 현재 READ OFF와 최초 데이터 0건은 유지합니다.
- 첫 시즌은 기존 편집 원고/안내·진행안의 **운영 입력용 묶음**으로 정리하며 아직 DB에 원고/일정/가격을 저장하지 않습니다.
- 실제 user journal 삭제 실행기, 보존 이관과 Auth 삭제, 결제 내역 법정 보존 분리, 관련 UI, 정식 개인정보처리방침 갱신 및 판매 전 종합 QA는 아직 미완료입니다.
- 기존 Draft PR #160과 Pages 전용 Draft PR #166을 유지하며 호스팅 main은 바꾸지 않습니다.
