# NAL READ BUILD22 — 실제 DB 1차 연결

## 적용 완료와 남은 범위

이번 단계에서는 `nal-platform`에 저장 구조와 DB 함수를 실제 적용했습니다. 이전 단계처럼 파일만 만든 상태가 아닙니다. 통합 원본 19개 중 앞의 5개 계층을 3개의 마이그레이션으로 적용했고, 나머지 14개 계층은 아직 적용하지 않았습니다.

| 실제 적용 이력 | 포함한 소스 |
| --- | --- |
| 20261007131539 / nal_read_build22_workspace_integration | BUILD04 WORKSPACE |
| 20261007131833 / nal_read_build22_editorial_report_integration | BUILD05 EDITORIAL + REPORT |
| 20261007132041 / nal_read_build22_join_account_integration | BUILD06 JOIN + ACCOUNT |

위 식별자는 Supabase에서 실제 반환한 적용 이력을 사용합니다. 같은 이름의 SQL 파일을 저장소의 `supabase/migrations/`에 보관합니다. 원문은 BUILD21 조립 입력 `3ccdbe665435734e5eb6f40922b49ddf9d8ff54e`의 해당 소스를 기반으로 하며, 이번 적용 SQL에는 공개 OFF·선행 구조·참가자 미등록·재실행 차단 조건을 추가했습니다. 배포된 결과가 예전 ZIP과 바이트 단위로 동일하다고 주장하지 않습니다.

## 실제 추가한 저장 구조

12개 비공개 테이블을 설치했습니다.

- 참가자 작업: 답변 초안, 작은 실험, LIVE 일정, 개인 대화 전후 메모, 중요한 문장 표시.
- 원고 관리: 편집 원고, 원고 변경·승인 이력.
- 리포트: 시점별 보관본.
- 참여 연결: 참가상품·이용 조건, 신청 확인 기록, 시작 안내 확인 기록.
- 계정: 화면 표시 이름과 수정 버전.

기존 질문 STEP에는 콘텐츠 연결 키, 시작·종료 비교 키와 버전, 리포트 연결 키 등 4개 필드를 추가했습니다. 원고·실험·참가자·진행안의 실제 내용이나 샘플 행을 삽입한 것은 아닙니다.

DB 함수는 8개입니다. 참가자 작업, 원고 구조 확인, 원고 편집, 리포트, 참가상품 조회, 참가권 연결, 소유자 상품 설정, 내 계정 조회/표시 이름 저장의 함수 정의를 설치했습니다. 이 숫자는 Edge Function 배포 수가 아닙니다. 이미 구현된 상위 계층과 최신 화면이 모두 연결됐다는 뜻도 아닙니다.

## 닫힌 상태에서의 적용

적용 전 읽기에서는 PostgreSQL 17 / FIX03까지의 기존 READ 이력, 공개 OFF, READ 참가자 미등록, 해당 신규 테이블 미존재를 확인했습니다. 기존 access/DAY 기반 정의도 첫 적용의 조건에 포함했습니다. 원래 전체 조립기의 조건을 지우고 억지로 실행하지 않았습니다.

각 마이그레이션은 자체 트랜잭션과 공개 OFF 확인을 사용했습니다. 따라서 이번 작업은 **3개의 실제 트랜잭션으로 앞부분만 적용한 통합 단계**이지, 19개를 한 트랜잭션으로 끝낸 실행이 아닙니다. 원고 승인·콘텐츠 공개·참가권 발급·실제 결제 함수를 실행하지 않았습니다.

적용 뒤에는 설치 이력과 테이블·함수 권한 메타데이터만 확인했습니다.

| 설치 확인 | 관찰 결과 |
| --- | --- |
| 새 테이블 | 12개 존재, 모두 RLS 사용 |
| 익명/로그인 브라우저 역할의 테이블 권한 | 없음 |
| 새 DB 함수 | 8개 존재, 모두 SECURITY INVOKER |
| 익명/로그인 브라우저 역할의 함수 실행 권한 | 없음 |
| 서버 역할의 함수 실행 권한 | 있음 |
| READ 공개 모드 | OFF 유지 |

보안 Advisor 조회에는 `rls_enabled_no_policy` INFO 항목 20개가 반환됐습니다. 비공개 서버 전용 테이블에 브라우저 정책을 추가해 개방하지 않았습니다. 직접 권한 조회에서도 이번 신규 테이블과 함수의 브라우저 역할 접근은 없었습니다. 이 확인은 업무 시나리오 테스트나 플랫폼 전체 보안 검토 완료를 뜻하지 않습니다.

참고: https://supabase.com/docs/guides/database/database-linter?lint=0008_rls_enabled_no_policy

## 기존 서비스와 데이터

카탈로그 31개, 설정 2개, 기존 PDF 파일 메타데이터 3개를 유지했습니다. 확인한 주문·READ 참가 등록·답변·운영자 멤버십 수는 모두 0이었습니다. 이 카운트는 일부 자료의 설치 전후 경계 확인이며, 전수 데이터 비교나 기능 테스트가 아닙니다.

기존 PDF 파일 자체, 무료 다운로드 코드, 결제사 설정, 실제 상품 가격, 모집일, 정원, 로그인 callback, 서버 환경값은 수정하지 않았습니다. 새 사용자/운영자 권한, 샘플 참가자, 첫 기수, 주문 또는 환불을 만들지 않았습니다. 기존 데이터베이스 안에 추가한 구조이므로 'DB도 변경 없음'이라고 보고해서는 안 됩니다.

## 아직 실행하지 않은 것

14개 후속 SQL 계층, Edge Function 배포, 웹 화면 배포, 실제 계정 로그인·결제·참가자 흐름, 첫 시즌 원고 저장과 공개 승인, main 병합, 고객 판매 활성화는 남아 있습니다. 단위 테스트·브라우저 테스트·결제/Auth 회귀 테스트는 실행하지 않았습니다. 설치 메타데이터 확인과 보안 Advisor 조회는 수행했습니다.

새 클라우드 프로젝트·유료 개발 브랜치·서버·구독·AI API를 만들지 않았습니다. 기존 프로젝트에 마이그레이션을 적용한 것이며, 미래 운영 비용이 항상 0원이라는 보장을 한 것은 아닙니다.

## 반드시 다음 작업에서 이어갈 기준

현재 DB는 더 이상 'FIX03까지만 존재하는 빈 통합 대상'이 아닙니다. BUILD20/21의 `after-fix03.forward.sql` 전체를 다시 실행하면 안 됩니다. 그 초기 기반 확인은 이 대상에서 실패하는 것이 맞으며, 조건문을 제거해서 재실행하지 않습니다.

`integration/nal-read/build22/resume-plan.json`에 적용한 5개와 남은 14개를 구분했습니다. 다음 순서는 BUILD07의 결제 기록/결과 반영/참가권 연결 DB 구조입니다. 이 구조의 설치는 실제 결제 실행이나 결제 활성화와 별개입니다. 이후 기수·정원·시작 안내·문의·홈·기수별 조회까지 남은 계층을 맞추고, 해당 버전의 서버와 화면을 연결해야 합니다.

기존 STORE 기반 마이그레이션 이름/버전 차이는 보정하지 않았습니다. `db reset`, 일괄 `db push`, 과거 이력 강제 repair 또는 모든 소스 재실행으로 그 차이를 숨기지 않습니다. 새 대상에서 복원할 때도 기존 기반과 실제 이력을 따로 대조해야 합니다.

기존 BUILD FIRST 규칙의 출판·판매·유료 리소스·테스트 경계는 계속 유지합니다. 이 문서는 이번 닫힌 DB 통합 실행을 기록하며, 후속 임의의 운영 변경을 일괄 승인하는 문서가 아닙니다.
