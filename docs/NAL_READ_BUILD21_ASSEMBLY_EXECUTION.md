# BUILD21 — execute the existing source assembler without paid artifact storage

## Scope
This step addresses the inability of the chat container to obtain a Git checkout. It does not add another participant/administration feature or replace the BUILD20 assembler with an unverified hand-written bundle.
A single-purpose GitHub Actions workflow runs only when the exact public-repository branch `integration/nal-read-build21` is deliberately created. That branch must contain this workflow and the existing BUILD20 assembler. Standard ubuntu-24.04 only; no larger runner, paid dependency, environment secret, Actions artifact upload or Actions cache is used.

The job checks out the exact triggering commit, runs the existing assembler, and records the generated archive, unapplied forward SQL, hashes, inventory and receipt under `integration/nal-read/build21/generated/` on that same integration branch. It never pushes main or feat/nal-read-v1 and uses a non-force push after comparing the remote branch head to the source commit. The input branch/code commit itself continues to use [skip ci]. Existing tests and release workflows are not changed or invoked by this workflow.

## Authority and disclosure
The job uses the repository's short-lived GITHUB_TOKEN, scoped to contents write for this one job solely to save source outputs back to its fixed branch. No customer credential, Supabase key, environment setting or user token is supplied. Existing repository permissions, branch protections and deployment rules are not modified. Checkout credentials are cleaned up by the pinned official checkout action after execution.
The repository is already public. Outputs contain only selected source files, the already-public metadata observation and derivative source assembly. They must not be confused with private operational data or installed DB objects. The `private/` name in the archive means not-for-web-root, not a promise of confidential hosting in a public repository.

## Work performed by the job
- Exact-commit checkout and source assembly; no application modules executed as tests.
- Existing 19-layer SQL candidate assembly with baseline guards; no SQL connection/execution.
- Matching frontend/API sources and asset labels collected by BUILD20.
- Generated byte/hash inventory and actual job receipt; no runtime PASS or security certification.
- One bounded archive saved in Git rather than billed artifact/cache storage. No release published, no site/deployment created and no user messages sent.

A GitHub Actions success would mean source assembly and its branch write completed, not that the customer platform works. If the job fails, no successful output receipt must be invented. The existing generator's checks stay intact; failures are addressed as source assembly issues, never by silently skipping required inputs or relaxing access guards.

## Runtime limits
This workflow does not apply schema, activate READ, configure login callbacks, change payment settings, issue enrollments, seed customer records, modify prices/dates or perform browser/Auth/payment/QA checks. Those remain at the owner's deliberate integration/pre-sale stage.
No deployment target is selected by the workflow. Actual migration history must be reconciled before applying the generated SQL candidate, especially the previously noted STORE foundation identifier difference.

## Result location
The output exists only after a successful completed job. Look at the integration branch's `integration/nal-read/build21/generated/RECEIPT.json` for the actual source SHA, archive hash/size, run ID and explicit not-deployed/not-tested fields. This source note alone is not proof that execution happened.
