# NAL 소셜 회원가입·PDF 구독 과금 설계

작성 기준: 2026-10-31, Asia/Seoul  
기준 소스: `dailycoach/home` main `8c14dd196c9d3a608102b7bbdecaa241bdd7eab8`  
작업 브랜치: `feat/nal-social-membership-20261031`  
문서 상태: **실행 가능한 설계안. 정기결제 백엔드·DB 변경·실제 청구는 이번 범위에서 구현하거나 실행하지 않았다.**

## 1. 결정 요약

NAL의 기존 무료 PDF는 비회원도 계속 이용할 수 있게 유지한다. 카카오·구글 회원가입은 내 계정과 구독을 관리하는 수단으로 추가한다. 무료 PDF를 받기 위해 새로 회원가입이나 결제를 강제하지 않는다.

유료 상품은 월간 PDF 구독 하나로 시작한다. **월 5,900원은 검증 전 가격 가설**이며, 공개 확정가나 현재 청구 중인 금액이 아니다. 출시 시 고객이 실제 지불할 최종 금액, 세무 처리, 발행 내용과 일정을 확정해야 한다.

핵심 상품안은 매월 심리학 교양 아트매거진 본편 1권과 그 호에 연결된 질문·실행지 1종이다. 실제 콘텐츠와 다음 발행 준비가 끝난 뒤 정기 발행을 약속한다. NAL 모임과 DAILYCOACHING 클래스 수강권은 이 PDF 구독에 포함하지 않는다.

회원의 기준 식별자는 기존 Supabase `auth.users.id` UUID다. 로그인 제공자 이름, 이메일 주소, 브라우저의 유료회원 표시를 결제 권한의 근거로 삼지 않는다. 서버가 확인한 결제와 이용기간을 근거로 비공개 PDF 다운로드를 허용한다.

## 2. 확인한 현재 구조와 이번 작업의 경계

### 2.1 재사용할 기반

| 영역 | 기준 소스에서 확인한 내용 | 해석 |
|---|---|---|
| 프런트엔드 | GitHub 저장소의 정적 NAL 페이지 및 GitHub Pages 배포 구조 | 소스 보관과 유료 서비스 운영 호스팅을 구분해야 함 |
| 데이터 프로젝트 | NAL 전용 Supabase `nal-platform`, ref `tdglznjjkgaulerbduwt` | 다른 ERP 프로젝트를 사용하거나 새 회원 DB를 중복 생성하지 않음 |
| 공개 데이터 | `nal_public_catalog()`와 `nal_catalog`, 공개용 설정 | 공개 메타데이터만 노출 |
| 회원 기반 | `auth.users`, `nal_profiles`, 소유자별 읽기 정책 | UUID를 기존 주문·권한과 연결 |
| 단건 결제 UI | `nal/assets/js/checkout.js` | 이메일 로그인 후 상품 1건 결제하는 흐름 |
| 단건 결제 서버 | `supabase/functions/nal-toss-checkout/` | 주문 생성, 금액 검증, `/v1/payments/confirm` 승인 |
| 결제 동기화 | `supabase/functions/nal-toss-webhook/` | 웹훅 값을 그대로 믿지 않고 PG 서버 조회로 확인 |
| 원장 | `nal_orders`, `nal_order_items`, `nal_payments` | 서버가 생성·조정하며 고객의 직접 쓰기 차단 |
| 파일 전달 | `nal_digital_entitlements`, `nal_private.product_files`, `nal-digital-download` | 결제·소유자·파일·기간 확인 후 짧은 서명 URL 발급 |
| 비공개 저장소 | 소스상 `nal-products-private` 버킷과 파일 등록 구조 | 운영 버킷·실제 원본·정책의 현재 상태는 출시 전 다시 확인 |

현재 결제와 다운로드 handler는 Supabase 사용자 조회 결과의 `email_confirmed_at`과 비익명 계정 여부를 검사한다. SQL의 주문 생성 및 다운로드 권한 검사에도 이메일 확인 조건이 있다. **소셜 로그인을 추가한다는 이유로 이 유료 이용 조건을 제거하지 않는다.**

저장소 안의 과거 문서에는 시점에 따라 미배포·배포·미활성화 기록이 함께 있다. 2026-10-31 공개 Auth 설정을 직접 조회한 결과 Kakao·Google provider는 모두 `false`였다. 공개 카탈로그의 회원·결제·보호 다운로드 기능도 꺼져 있다. 이 문서는 소스가 있다는 사실을 실제 거래 성공의 증거로 취급하지 않는다. 외부 앱·시크릿, PG 계약, 원본 파일 존재 여부는 출시 전 별도 확인 대상이다. 자세한 확인 기록과 정확한 callback은 [회원가입 개통 인계서](NAL_SOCIAL_MEMBERSHIP_SETUP_20261031.md)를 따른다.

### 2.2 단건 결제와 정기결제의 차이

| 항목 | 기존 단건 checkout | 새로 설계한 월 구독 |
|---|---|---|
| 고객 행동 | 매번 상품 결제 인증 | 최초 결제수단 등록·정기결제 동의 |
| PG 호출 | `POST /v1/payments/confirm` | 빌링키 발급 후 `POST /v1/billing/{billingKey}` |
| 주문 단위 | 상품 구매 1건 | 구독의 한 회차에 연결된 결제 시도 |
| 권한 | 구매한 파일의 사용권 | 결제한 기간의 유료 자료실 이용권 |
| 반복 실행 | 없음 | 서버 스케줄러·작업 점유·대사 필요 |
| 해지 | 주문 취소·환불 | 다음 자동갱신 중지와 이미 낸 금액의 환불을 구분 |
| 현재 상태 | 소스 존재, 실거래 연결 상태 미확인 | 설계만 완료, 새 백엔드·테이블 없음 |

기존 결제 버튼의 문구를 ‘구독’으로 바꾸는 것만으로 정기결제가 되지 않는다. 기존 상품 구매 RPC에 매월 반복 호출을 붙이는 방식도 구독 회차·해지·중복결제 통제를 제공하지 못한다.

### 2.3 이번 브랜치에서 병행한 회원 UI

문서 작성 중 같은 작업 브랜치에 `nal/login/`, `nal/auth/callback/`, `nal/my/account/`, `member-auth.js`, `member-pages.js`, `nal-membership.css`, `membership.json`이 추가된 것을 확인했다. 소스에는 카카오·구글 선택, PKCE 콜백 처리, 서버 사용자 확인, 약관 동의·표시명 입력, 계정 표시·로그아웃, 유료 PDF 준비 안내가 포함된다.

이는 **회원 UI와 연동 코드가 작성된 상태**다. 확인 당시 `membership.json`의 `authEnabled`는 `false`, `policyVersion`은 `null`이며 실제 provider 준비와 정책 버전이 확인되기 전에 가입을 열지 않도록 구성되어 있다. 이 소스 확인만으로 실제 OAuth 로그인, 운영 배포 또는 유료 구독이 완료되었다고 표현하지 않는다. 회원 UI의 최종 검증 결과는 해당 구현 보고를 따른다.

## 3. 상품·가격·자료 이용 정책

### 3.1 두 가지 이용 형태

| 항목 | 무료 이용 | PDF 월 구독 |
|---|---|---|
| 회원가입 | 기존 무료 PDF 이용에는 불필요 | 카카오·구글 로그인 및 필요한 계정 확인 |
| 가격 | 0원 | 월 5,900원 가설 |
| 기존 무료 PDF | 계속 공개 | 동일하게 이용 |
| 신규 콘텐츠 | 공개호·미리보기·선정한 무료 콘텐츠 | 월간 본편 1권 + 연결 질문·실행지 1종 제안 |
| 유료 지난 호 | 표지·목차·미리보기 | 유효한 구독기간 중 공개된 구독 자료실 이용 |
| 다운로드 | 무료 공개 링크 유지 | 서버에서 회원·결제기간 확인 후 발급 |
| 해지 | 해당 없음 | 다음 자동갱신을 중지하고 결제한 기간까지 이용 |
| 개인 보관 | 허용 | 유효기간 중 정상 다운로드한 파일의 개인 보관 허용 |
| 모임·강의 | 별도 상품 | 별도 상품 |

무료 이용자를 자동으로 유료 구독에 넣지 않는다. 초기에는 무료체험 종료 후 자동과금이나 여러 요금제, 연간 선결제를 추가하지 않는다. 유료호와 발행 운영이 준비된 상태에서 고객이 명시적으로 월 구독을 선택하도록 한다.

가격의 유효성은 첫 결제 전환율, 다음 달 갱신율, 실제 콘텐츠 이용, 환불 사유, 콘텐츠 제작 시간을 확인해 판단한다. 월 5,900원 기준 100명은 590,000원, 300명은 1,770,000원, 1,000명은 5,900,000원의 월 총결제액이다. 이는 수요 예측이나 순이익이 아니라 단순 산술이다.

### 3.2 개인 이용과 자료실

구독은 개인 1명의 읽기·기록·개인 인쇄를 위한 사용권이다. 개인 기기에 정상 다운로드한 파일은 구독 종료 후에도 보관할 수 있다. 파일 공유, 재판매, 온라인 재업로드, 강의·기관의 단체 배포 권한은 포함하지 않는다. 강사·기관 사용권은 필요할 때 별도로 설계한다.

구독이 끝나면 새 유료 파일의 다운로드와 유료 자료실 접근을 중지한다. 이미 다운로드된 파일을 원격으로 삭제하거나 회수할 수 있다고 안내하지 않는다. 재구독하면 그때 운영 중인 구독 자료실 이용권을 다시 부여한다. 공개되어 있던 기존 무료 자료의 접근은 이 상태와 무관하게 유지한다.

한 번 구독하고 자료를 내려받은 뒤 해지하는 행동을 인위적인 단계나 숨겨진 제한으로 막지 않는다. 다음 호의 품질과 정기 발행이 구독 유지의 근거가 되어야 한다. 다운로드 제한이 필요하면 장애·자동 수집 방지 목적의 공정 이용 정책으로 사전에 표시하고, 정상 이용자가 반복 시도 때문에 막히지 않게 한다.

## 4. 호스팅과 서비스 경계

GitHub 공식 Pages 제한은 온라인 비즈니스·전자상거래·상업 거래 촉진을 주목적으로 하는 서비스의 무료 호스팅 용도를 허용하지 않는다고 설명한다. 따라서 현재 Pages에 유료 구독을 그대로 활성화하는 것을 출시 완료로 볼 수 없다. [공식 근거 S1](#공식-자료)

권하는 운영 목표는 **GitHub를 소스·버전 보관에 유지하고, NAL 유료 회원·구독 화면과 해당 런타임을 Cloudflare 쪽으로 운영하는 구조**다. 기존 Supabase의 Auth·DB·비공개 Storage는 재사용한다. 서버 코드를 Cloudflare Workers와 Supabase Edge Functions 중 어디에 둘지는 기존 함수 재사용성, 작업 실행 시간, 스케줄러 운영 방식에 맞춰 확정한다. 서버를 옮겨도 결제 원장과 이용권의 단일 기준은 Supabase로 유지한다.

이번 범위는 호스팅 전환 설계다. 기존 `daily-coach-ing.com` 전체의 DNS·호스팅을 바꾸거나 다른 서비스까지 이전하지 않는다. 전용 하위 도메인 또는 NAL 경로 이전 중 하나를 선택하고, 기존 URL·로그인 리디렉션·무료 파일·검색 유입을 점검한 뒤 별도 전환 범위를 확정한다. 실제 Cloudflare 계정·프로젝트·요금제·도메인 설정을 확보했다는 뜻도 아니다.

유료 런타임 출시 전까지 결제 활성화 플래그를 닫아 둔다. 무료 PDF 페이지, 무료 파일, 기존 모임 안내는 현재 동선을 유지하며 과금 설계 때문에 임의로 차단하지 않는다.

## 5. 회원가입부터 이용권까지

### 5.1 공통 원칙

카카오 계정 로그인과 구글 로그인은 같은 NAL 회원 체계를 사용한다. 제공자의 계정 식별자는 Supabase Auth의 identity와 연결하고, 주문·구독·다운로드 기록의 소유자는 `auth.users.id`로 고정한다.

이메일이 같다는 이유만으로 별도 계정의 주문과 구독을 프런트엔드에서 합치지 않는다. 같은 검증 이메일의 자동 identity 연결은 Supabase Auth의 공식 동작에 맡긴다. 서로 다른 이메일의 계정을 수동 연결하는 UI는 이번 범위 밖이며, 추가한다면 기존 계정 로그인과 추가 제공자의 본인 인증·충돌 검사를 거치는 별도 절차로 구현한다. 이메일 주소가 바뀌어도 구매 권한의 소유자는 기존 UUID다. [Supabase identity 연결](https://supabase.com/docs/guides/auth/auth-identity-linking)

카카오 로그인은 카카오톡 오픈채팅 자동 입장, 친구 추가, 마케팅 수신 동의를 의미하지 않는다. 구글 로그인도 다른 구글 자료의 접근 권한을 요구하지 않는다. 프로필 표시명 외에 전화번호·실명·추가 정보는 구독에 꼭 필요한 시점과 목적이 있을 때만 별도 수집한다.

### 5.2 이메일이 없는 카카오 회원

현재 유료 주문·다운로드의 `email_confirmed_at` 검사를 유지한다. 카카오에서 이메일이 없거나 필요한 동의를 받지 못한 경우에도 기본 로그인 상태와 무료 이용은 설명하되, 유료 구매 전에 확인 가능한 이메일을 추가·검증하도록 한다.

Supabase의 카카오 provider가 해당 계정·동의 조합을 실제로 처리하는지 외부 계정으로 검증해야 한다. 이메일이 없으면 provider 단계에서 로그인 자체가 실패하는 경우까지 포함해 점검한다. 이때 임의 이메일 생성, `email_confirmed_at` 조작, 기존 유료 보안 조건 삭제로 우회하지 않는다. 필요한 카카오 동의항목과 계정 확인 흐름을 구성하거나 확인된 구글·이메일 경로를 안내한다.

### 5.3 사용자 화면

| 화면 | 보여 줄 핵심 내용 |
|---|---|
| 로그인 | 카카오로 시작하기, Google로 시작하기, 약관·개인정보 안내 |
| 계정 확인 | 표시명, 연결한 로그인 방법, 필요한 이메일 확인 상태 |
| 구독 소개 | 최종 결제금액, 매월 제공물, 실제 제공 시작일, 미리보기, 해지·환불 안내 |
| 결제 직전 | 첫 결제금액, 갱신 주기, 다음 예정일, 정기결제 동의와 약관 버전 |
| 내 구독 | 현재 이용 종료일, 다음 결제일, 결제내역, 결제수단 변경, 자동갱신 해지 |
| 내 자료실 | 무료·유료 구분, 이번 호, 지난 호, 실제 다운로드 가능 상태 |
| 처리 지연 | 결과 확인 중이라는 상태와 주문번호. 다시 누르면 새 청구가 생기지 않음 |

성공 URL로 돌아왔다는 이유로 유료회원으로 바꾸지 않는다. 서버가 확인한 결과가 오기 전에는 ‘확인 중’을 표시한다.

## 6. 데이터 설계

아래 테이블명·필드는 **후속 구현을 위한 제안**이다. 이번 문서 작성으로 운영 DB에 생성되지 않았다. 기존 주문·결제 테이블을 재사용하되 정기구독을 단건 상품처럼 취급하지 않도록 연결 테이블과 전용 권한을 추가한다.

### 6.1 엔터티와 제약

| 엔터티 | 필수 정보 | 주요 제약·소유권 |
|---|---|---|
| `auth.users`·`nal_profiles` | `user_id`, 표시명, 이메일 확인 상태 | UUID를 소유자 기준으로 사용. 프로필 변경으로 유료 등급 변경 불가 |
| `nal_membership_plans` | `plan_id`, `version`, `amount_won`, `currency`, `interval_months`, `published`, `policy_version` | `unique(plan_id, version)`, 금액 양의 정수, 초기 `KRW`·1개월. 가격 버전은 사용 후 불변 |

| `nal_private.refund_events` | 결제, PG 취소 식별자, 금액, 사유, 처리 상태·시각 | PG 취소 식별자 고유. 누적 환불액≤승인액을 잠금·트랜잭션으로 검증 |
| `nal_private.provider_events` | PG, 환경, 이벤트 ID 또는 중복 판별값, 검증 상태, 처리 상태·시각 | 동일 이벤트 중복 처리 방지. 원문 저장은 필요한 필드만 암호화·보존기간 적용 |
| `nal_consents` 및 감사 기록 | 회원, 문서·상품·정책 버전, 동의·변경 시각, 처리 주체 | 사후 덮어쓰기보다 변경 이력 추가. 마케팅 동의와 결제 동의 분리 |

회차 하나에 실패한 결제 시도가 여러 개 있을 수 있지만, 성공 청구는 하나만 인정한다. 확실히 실패한 시도 뒤에 새 시도를 만들 때도 회차 잠금과 성공 결제 유무를 먼저 확인한다. 응답을 잃은 `unknown` 시도는 실패 시도와 다르게 처리한다.

서로 다른 테이블의 회원·금액·통화·기간 일치나 환불 합계는 단순 `CHECK` 하나로 해결되지 않는다. 외래키와 고유 제약, 서버 전용 조정 함수, 행 잠금 및 트랜잭션을 함께 사용한다. 결제 확정과 이용권 생성은 같은 DB 트랜잭션으로 처리한다.

현재 단건 권한은 주문·상품·파일에 연결되어 있다. 구독 자료실 권한을 기존 `nal_digital_entitlements`에 가짜 상품 구매로 삽입하지 않는다. 구독 이용권을 확인하는 별도 서버 경로를 추가하고 기존 단건 구매자의 권한 검사도 유지한다.

### 6.2 RLS와 사용자 쓰기 금지

노출 스키마의 모든 신규 테이블에 RLS를 적용하고 실제 GRANT도 함께 제한한다. 공개 카탈로그·발행 메타데이터는 공개 행만 조회한다. 회원용 구독·결제·권한 조회는 `auth.uid() = user_id` 또는 소유 주문과의 검증된 연결 조건을 사용한다. 조회용 뷰는 `security_invoker` 등 권한을 보존하는 방식으로 제공한다. [공식 근거 S7](#공식-자료)

`anon`·`authenticated` 역할은 구독 금액, 자동갱신 상태, 결제 상태, 회차, 이용권, 환불 원장, 빌링키, 다운로드 카운터를 직접 INSERT·UPDATE·DELETE하지 못한다. 사용자의 해지 요청도 인증된 서버 엔드포인트가 본인 소유권과 현재 상태를 검사한 뒤 수행한다. 프로필의 사용자 수정 가능 항목에 결제·관리자 권한 필드를 넣지 않는다.

`user_metadata`, localStorage, URL 파라미터의 `isPaid`, 브라우저가 전송한 관리자 여부는 권한 근거로 쓰지 않는다. 서비스 키·PG 시크릿·빌링키는 서버 전용 비밀 저장소에서 관리한다. 운영자 권한은 기존 `nal_private.admins`의 검증된 UUID 명단으로 관리한다.

## 7. 결제 처리와 장애 복구

### 7.1 첫 결제

1. 서버가 로그인 토큰을 검증하고 본인 UUID, 비익명 계정, 이메일 확인, 상품 공개 상태와 실제 제공 준비를 확인한다.
2. 서버가 상품·가격·약관 버전을 고정하고 최초 회차 및 시도를 생성한다. 고객의 정기결제 동의도 해당 버전에 연결한다.
3. 토스 등록창에서 결제수단을 인증한다. 직접 카드번호를 NAL 폼으로 받는 방식을 초기 구현에서 사용하지 않는다.
4. 돌아온 `authKey`와 `customerKey`를 로그인 회원 및 진행 중인 등록 요청과 대조한 뒤 서버에서 빌링키를 발급한다. 재사용·다른 회원으로의 연결을 차단한다.
5. 빌링키를 안전하게 저장한 뒤 첫 결제 승인 API를 호출한다. **카드 등록이나 빌링키 발급만으로 이용권을 만들지 않는다.**
6. 서버가 PG 응답의 주문번호, 금액, 통화, 결제 상태와 환경·상점 정보를 검증한다.
7. 결제 원장·회차 상태·이용권을 확정한 뒤 고객에게 이용 종료일과 다음 결제일을 표시한다.

토스 자동결제는 추가 계약·리스크 검토 대상이며, 정기 실행은 가맹점 서버가 구현해야 한다. 실제 계약 완료 전에는 테스트 환경만 연결한다. [공식 근거 S2](#공식-자료)

### 7.2 월말과 한국 시간 기준

월 구독은 30일 고정이 아니라 **달력 기준 1개월**로 정의한다. 날짜 계산은 `Asia/Seoul`에서 수행하고 실제 시각은 UTC `timestamptz`로 저장한다. 가입 당시의 `anchor_day`와 현지 시각을 보존한다.

예를 들어 1월 31일 10:30 가입이면 평년 2월 28일 10:30, 3월 31일 10:30을 다음 경계로 계산한다. 2월 말일로 보정되었다고 이후 매월 28일로 밀리지 않는다. 이용기간은 `[valid_from, valid_until)`로 취급해 끝 시각의 중복 권한을 막는다. 윤년·연말·월말을 수용 테스트에 포함한다.

갱신 실패 후 오랜 시간이 지나 고객이 다시 결제하는 경우, 이미 이용하지 못한 과거 회차를 조용히 일괄 청구하지 않는다. 초기에는 자동 재시도를 생략하고, 고객이 재결제를 선택할 때 제공할 기간·금액·새 기준일을 명확히 확정하는 방식으로 단순화한다. 결과 불명 거래의 대사는 자동 재시도와 별개로 계속한다.

### 7.3 중복결제 방지와 작업 점유

스케줄러는 예정 회차를 생성하는 역할만 맡고, 작업자는 DB 트랜잭션에서 회차와 구독 상태를 확인하여 일정 시간의 실행 권한인 lease를 얻는다. `lease_owner`, `lease_until`, 증가하는 `fencing_token`을 사용해 이전 작업자가 뒤늦게 DB를 덮어쓰지 못하게 한다.

외부 PG 호출 전에는 자동갱신 중지 여부와 구독 revision을 다시 확인하고 시도를 `dispatching`으로 기록한다. 외부 네트워크 응답을 기다리는 동안 DB 행 잠금을 계속 잡지 않는다. lease가 만료되었다는 이유만으로 새 주문번호를 만들어 다시 청구하지 않는다. 이미 송신된 시도는 대사 작업으로 넘긴다.

같은 시도의 재전송은 주문번호·멱등키·금액·요청 지문을 그대로 사용한다. 토스 멱등키의 유효기간은 15일이므로 회차별 고유 제약과 영구 원장을 병행한다. 15일이 지난 불확실 거래를 새 키로 바로 청구하지 않고 PG와 대사한다. [공식 근거 S3](#공식-자료)

### 7.4 `unknown`과 대사

| 상황 | 기록할 상태 | 후속 행동 |
|---|---|---|
| 명확한 승인 성공 | `succeeded` | 원장·이용권 트랜잭션 확정 |
| PG가 확정적인 거절 응답 | `failed` | 새 유료기간을 열지 않고 결제수단 변경 안내 |
| 네트워크 타임아웃·응답 소실 | `unknown` | 새 청구 차단, 같은 주문을 PG에서 조회 |
| 승인 성공 후 DB 저장 실패 | `reconcile_pending` | 같은 결제 식별자로 원장·권한을 재조정 |
| 조회도 일시 실패 | `unknown` 유지 | 지연 재조회·운영 경보, 고객에게 결과 확인 중 표시 |
| PG 승인과 환불이 교차 도착 | 원장 이력 확인 | 현재 PG 상태와 취소 원장에 맞춰 권한 조정 |

기존 단건 함수의 10초 네트워크 타임아웃을 빌링 구현에 그대로 복사하지 않는다. 선택한 자동결제 API의 응답 시간과 실행 환경 제한을 확인하고, 응답 대기를 감당할 서버 작업 또는 비동기 복구 흐름을 구성한다. 작업 재시작과 네트워크 재전송을 실제 신규 결제로 오해하지 않게 한다.

### 7.5 해지와 청구의 동시 발생

해지 요청은 구독 행을 잠그고 `renew_enabled=false`, 해지 시각, revision 증가를 원자적으로 기록한다. 아직 외부로 송신하지 않은 다음 회차 작업은 취소한다. 같은 요청을 반복해도 결과가 바뀌거나 수수료가 발생하지 않는다.

PG 송신 직전 재검사보다 해지가 먼저 확정되었다면 청구하지 않는다. 이미 PG로 전송된 순간 이후에는 요청을 되돌릴 수 있다고 가정하지 않는다. 이 경우 고객에게 처리 중인 회차를 표시하고 PG 조회로 결과를 확인한다. 해지와 충돌한 새 갱신이 승인되면 승인 시각·해지 시각·콘텐츠 제공 상태를 바탕으로 정해 둔 정책에 따라 취소·환불하며, 확인 전 불필요한 새 콘텐츠 제공을 보류한다.

이미 결제한 유효기간의 이용권은 정상 해지만으로 즉시 지우지 않는다. 미래 갱신 중지와 이번 기간 환불은 별도 처리다. 회원 탈퇴도 미래 청구를 먼저 중지한 뒤 진행 중인 결제를 정리해야 하며, 기존 결제 원장을 무조건 cascade 삭제하지 않는다.

### 7.6 웹훅

토스 공식 문서에 따르면 자동결제는 승인 완료 때 `PAYMENT_STATUS_CHANGED` 웹훅을 보내지 않는다. **성공 웹훅을 기다리는 방식으로 첫 권한이나 갱신 권한을 부여하지 않는다.** 서버 승인 응답과 조회·대사를 기준으로 처리하고 취소·빌링키 삭제 등의 이벤트를 보조 동기화에 사용한다. [공식 근거 S4](#공식-자료)

선택한 webhook 버전의 보안 키와 HMAC 서명을 검증하고 원문 body를 보존하여 검증한다. 허용한 시간 범위, 환경·상점, 주문 소유권, 금액을 함께 검사한다. 최신 문서가 설명하는 복수 서명을 처리하고, 재전송 때 달라지는 transmission ID를 이벤트 중복 키로 쓰지 않는다. 검증된 이벤트를 내구성 있게 수신 기록한 뒤 성공 응답하고 후속 처리를 멱등하게 수행한다.

## 8. 비공개 PDF 전달

유료 원본은 GitHub 저장소, 공개 assets 폴더, 공개 JSON, HTML의 숨겨진 속성, 공개 버킷에 넣지 않는다. 공개 데이터에는 표지·목차·미리보기와 발행 정보만 둔다. 비공개 파일 경로와 Storage 서명값도 공개 카탈로그에 포함하지 않는다.

다운로드 요청마다 서버가 세션, 본인 UUID, 이메일 확인, 유효한 회차 이용권, 환불·권한 취소 여부, 파일의 실제 존재·활성 상태를 확인한다. 구독자의 다운로드는 단건 구매용 권한을 가장하지 않고 구독용 검사 경로를 사용한다.

서명 URL 유효기간의 초기 제안은 60~120초이며 네트워크·모바일 UX를 확인해 확정한다. 실제 TTL은 남은 이용권 시간보다 길지 않게 한다. 기존 단건 전달 코드는 최대 600초로 제한되어 있으므로 구독 TTL은 별도로 검토한다. 브라우저 응답은 `Cache-Control: no-store`로 처리하고 URL이 분석 도구·오류 로그·리퍼러에 남지 않게 한다.

**개별 Supabase 서명 URL은 발급 뒤 직접 취소할 수 없다.** 구독 해지나 Auth 키 변경만으로 이미 발급된 URL이 즉시 무효가 되지 않는다. 짧은 TTL은 노출 시간을 줄이는 수단이며, 즉시 회수 보장이나 다운로드 후 복제 방지는 아니다. 꼭 더 강한 통제가 필요하면 요청마다 권한을 검사하는 서버 전달 방식을 따로 검토한다. [공식 근거 S6](#공식-자료)

이미 로컬 기기에 저장된 PDF는 삭제할 수 없으므로 기술적 보호 범위와 개인 이용 약관을 일치시킨다. 보안 때문에 고객 이름·이메일을 PDF에 공개 삽입하는 방식은 기본값으로 두지 않는다.

## 9. 해지·환불·고지

구독 화면과 결제 직전에 최종 결제금액, 결제 주기, 제공물, 제공 시점, 이용기간, 자동갱신 여부, 해지 방법, 환불 신청 방법을 보여 준다. 체크박스의 선택 여부뿐 아니라 동의한 문서·가격·상품 버전과 시각을 서버에 기록한다.

‘PDF는 환불 불가’라는 포괄 문구를 쓰지 않는다. 현행 전자상거래법은 디지털콘텐츠의 제공 개시, 제공하지 않은 가분적 부분, 고지·시험 사용 조치, 계약과 다르게 제공된 경우 등을 구분한다. 미리보기와 명확한 제공 조건을 준비하고, 실제 제공 기록과 환불 정책을 검토한다. [공식 근거 S8](#공식-자료)

| 요청 | 기본 처리 방향 |
|---|---|
| 다음 달부터 해지 | 즉시 자동갱신 중지, 기존 결제기간 유지 |
| 이번 결제 환불 | 별도 환불 접수 후 제공 내역·법정 권리·정책에 따라 판단 |
| 중복 청구 | 회차·PG 원장 대사 후 잘못된 중복 거래 취소 |
| 결제했으나 자료 접근 실패 | 먼저 권한 복구·장애 확인, 제공 불능 시 적정 환불 |
| 약속한 콘텐츠 미발행 | 미제공 부분과 계약 내용에 따라 보상·환불 처리 |
| 결제금액 인상·무료에서 유료 전환 | 법정 동의·고지 절차 후 새 조건 적용. 기존 가격 조용한 변경 금지 |

법정 권리를 약관으로 없애거나 ‘다운로드 버튼을 눌렀다’는 이유만으로 모든 환불을 자동 거절하지 않는다. 환불 성공은 PG 처리 결과로 확인하고, 금액·거래·권한 조정을 감사 기록에 남긴다. 부분 환불은 기존 단건 로직의 전체 권한 취소를 무조건 재사용하지 않고 제공 범위와 정책에 맞춰 처리한다.

기존 코칭 매출의 세무 처리만으로 PDF 구독의 면세 여부를 확정하지 않는다. 최종 상품 구성과 사업자 상태를 기준으로 세무 처리를 확인한다. 결제 UI에는 고객이 실제로 결제할 총액을 표시한다.

## 10. PG 준비 전 대안과 비용

자동결제 추가 계약이 완료되지 않았지만 일반결제의 계약·파일·호스팅·환불 준비는 끝났다면 **단건 30일 이용권**을 별도 상품으로 제공할 수 있다. 이는 한 번 결제하고 종료되는 이용권이며 자동갱신하지 않는다. 화면에도 ‘30일 이용권 · 자동결제 없음’이라고 표시한다. 이 대안을 도입한다고 기존 미완료 PG 설정을 우회할 수 있는 것은 아니다.

토스 공개 비용표의 일반 안내는 최초 가입비 220,000원, 연관리비 110,000원, 일반 카드 3.4%이며 결제 수수료 VAT는 별도다. 계약 형태·적용 등급 등에 따라 실제 조건이 달라질 수 있으므로 NAL의 자동결제 견적으로 확정하지 않는다. 테스트 계정이나 코드 준비가 실제 운영 무비용을 보장하지 않는다. [공식 근거 S5](#공식-자료)

이번 작업은 PG 계약 체결, 가입비 결제, 유료 인프라 가입, 고객 카드 청구를 수행하지 않는다. 실제 비용과 운영 조건을 확인한 뒤 출시 작업에 반영한다.

## 11. 출시 수용 기준

다음은 후속 구현과 실설정이 완료되었을 때 통과해야 할 기준이다. 이 문서의 체크리스트가 테스트 통과 기록을 의미하지 않는다.

| 영역 | 반드시 확인할 결과 |
|---|---|
| 실제 소셜 로그인 | 외부 카카오·구글 계정으로 가입·재로그인·로그아웃·새 기기 복귀 성공 |
| 콜백 보안 | 허용 origin·redirect만 사용, 취소·state 오류·재사용·외부 next URL 거부 |
| 카카오 이메일 | 이메일 없는 계정·동의 거부·미검증 조합의 실제 동작 확인, 유료 조건 우회 불가 |
| 계정 연결 | 기존 구매 UUID 보존, 다른 계정의 주문·구독으로 잘못 합쳐지지 않음 |
| 결제 테스트 | 실제 PG 테스트 상점에서 등록→첫 승인→원장→권한→다운로드 완료 |
| 카드 등록만 성공 | 결제하지 않은 계정은 유료 자료 다운로드 불가 |
| 금액·소유권 | 브라우저 가격 변경, 다른 주문번호, 다른 계정 토큰, 결제 식별자 재사용 거부 |
| 중복 작업 | 동시에 두 작업자가 같은 회차를 처리해도 승인 1건·권한 1개 |
| 결과 불명 | 승인 후 응답 소실·DB 실패를 재현하고 추가 청구 없이 복구 |
| 월말·시간 | 29·30·31일, 윤년 2월, 연말, 한국 시간 경계 계산 일치 |
| 해지 경쟁 | 작업 점유 전·송신 직전·송신 후 해지에서 중복 또는 방치된 청구 없음 |
| 웹훅 | 위조·재전송·순서 역전 처리, 자동결제 성공 웹훅 없이 권한 정상 생성 |
| PDF 보호 | 비회원·타인·기간 종료·환불 계정 차단, 원본 공개 주소 없음 |
| URL 만료 | TTL 뒤 서명 URL 만료, 취소 직후 발급분의 남은 TTL 한계 확인 |
| 무료 이용 | 비회원 기존 무료 PDF의 링크·다운로드·모바일 동작 유지 |
| 운영 복구 | 결제수단 변경, 갱신 실패, 환불, 공급 장애, 운영 알림과 대사 경로 검증 |
| 호스팅 | 상거래 운영이 가능한 런타임·도메인·TLS·리디렉션 구성 완료 |
| 콘텐츠·정책 | 실물 PDF·미리보기·발행 운영·고객 최종가·약관·환불 안내 확인 |

운영 활성화는 설정을 모두 넣은 뒤 마지막에 한다. 실제 고객을 대상으로 한 소액 청구를 테스트처럼 임의 수행하지 않는다. 테스트키 결과와 운영 계약·라이브키 준비를 구분하고, 라이브 거래 검증은 대상·금액·취소 방식을 정한 승인된 운영 절차에서 진행한다.
