# NAL READ BUILD26 — 문의와 참가자 홈 DB 연결

## 실제 적용 결과

기존 nal-platform에 BUILD12 SUPPORT와 BUILD14 HOME 두 계층을 한 마이그레이션으로 적용했습니다. 성공 응답 뒤 실제 설치 이력에서 `20261007211433 / nal_read_build26_support_home_integration`을 확인했습니다. 누적 SQL 소스 계층은 19개 중 16개이며, 플랫폼 전체 완성률이나 고객 기능 검증 점수가 아닙니다.

기준 소스는 `3ccdbe665435734e5eb6f40922b49ddf9d8ff54e`입니다. 앞의 14개는 재실행하지 않았습니다. 기존 통합 잠금, 여섯 선행 마이그레이션 이력, PostgreSQL 17, READ OFF, 기존 계정 함수 정의, 신규 객체 미존재, 주문·참가 등록 미존재 조건을 붙인 후속 변경분입니다. 원문 함수 로직을 재설계하지 않고 두 소스의 외곽 트랜잭션을 합쳤습니다. 적용문에 추가된 가드와 주석 차이가 있으므로 옛 ZIP과 바이트가 같다는 뜻은 아닙니다.

설치 관찰 시각은 2026-10-07 21:14:52 UTC, 한국 시간으로 2026년 10월 8일 06:14:52입니다. 저장소 SQL 파일명은 실제 적용 이력의 UTC 기반 식별자를 사용합니다.

## 문의를 같은 대화 안에서 이어가기

새 비공개 테이블은 세 개입니다. support_threads는 문의 제목·분류·처리 상태·담당자·읽음 위치를, support_messages는 본문과 답변 순서를, support_commands는 재전송한 요청의 중복 처리를 구분하는 기록을 저장합니다. 요청 기록에는 메시지 본문을 다시 복제하지 않습니다.

참가자는 자기 문의만 조회합니다. 기수나 주문을 연결할 때도 본인에게 실제로 연결된 기록인지 확인하고, 함께 선택한 주문과 시즌이 서로 다른 경우에는 거부합니다. 기수·주문 연결 없이 일반 문의를 남기는 기존 설계도 유지합니다. 문의 처리는 신원이 확인된 계정을 요구하지만, 유효한 READ 참가권 자체를 요구하지는 않습니다. 따라서 나중에 API가 연결되면 참가권 접근 문제도 문의할 수 있는 구조입니다. 로그인 없이 쓰는 고객지원 기능을 추가한 것은 아닙니다.

운영자 화면은 소유자 또는 해당 문의에 현재 배정된 운영자만 조회·답변하도록 제한합니다. 담당자 변경은 소유자가 기존 운영자 중에서 선택하는 명시적 동작이며, 새 운영자 권한을 부여하지 않습니다. 같은 요청 ID를 같은 내용으로 재전송하면 이전 처리 결과를 돌려주고, 다른 내용으로 재사용하면 충돌로 처리합니다. 해결됨·다시 열기·답변 추가도 현재 버전과 사용자 확인을 요구합니다.

문의는 참가자가 직접 입력한 내용과 선택한 최소 기수·주문 정보를 다룹니다. 코칭 질문의 답변이나 실험 성찰을 자동 첨부하지 않습니다. 결제 상태·참가권·환불을 문의 함수가 수정하지 않으며, 문자·이메일·외부 메신저 전송을 추가하지 않았습니다.

## 답변을 발견할 참가자 홈까지 연결

기존 계정 함수는 nal_private.account_before_home으로 보존하고, home 요청만 새 읽기 전용 조회로 연결합니다. 기존 표시 이름·주문·자료·프로그램·리포트 동작은 이전 구현으로 전달합니다.

홈 조회는 현재 계정의 이어갈 질문, 다가오는 LIVE, 읽지 않은 운영자 답변, 대기 중인 참여 제안, 확인이 필요한 주문 상태를 묶습니다. 기존에 저장된 실제 상태만 사용하며, 없는 자료를 가상 숫자로 채우지 않습니다. 일부 기능을 읽지 못하면 unavailable, 서버 설정상 닫혀 있으면 disabled로 구분합니다. 제한된 목록에는 조회 범위와 한도를 함께 남깁니다.

홈에서는 문의 본문을 읽지 않고 제목·상태·답변 시각을 제시합니다. 홈을 여는 것만으로 문의를 읽음 처리하거나, DAY를 시작하거나, 대기를 수락하거나, 결제사 상태를 조회·반영하지 않습니다. 실제 대화의 읽음 위치는 기존 별도 요청으로만 저장합니다. 서버에서 전달하는 기존 기능 설정을 받아 사용하며, 브라우저가 임의로 기능이나 역할을 켜는 경로를 만들지 않습니다.

## 설치 후 확인 범위

세 신규 테이블은 모두 RLS가 켜져 있고 익명·로그인 브라우저 역할의 직접 권한이 없습니다. 문의 본문과 중복 요청 기록은 서버 역할에도 수정 권한 없이 조회·추가만 허용합니다. 문의 상태 테이블에는 기존 업무 처리를 위한 수정 권한이 있습니다.

조회한 함수 객체는 8개이며 보존된 이전 계정 구현을 포함합니다. 모두 SECURITY INVOKER이고, 브라우저 역할의 직접 실행은 불가하며 service_role 실행은 허용됩니다. 새 Edge Function 8개를 배포했다는 의미가 아닙니다.

READ 공개 모드는 OFF였고 세 문의 테이블은 모두 0행이었습니다. 기존 주문·결제·READ 등록·답변·운영자 멤버십도 0으로 확인됐습니다. 제한된 집계에서 카탈로그 31개·설정 2개·기존 PDF 파일 메타데이터 3개를 확인했습니다. 이 집계는 전수 데이터 동일성 검사나 고객 시나리오 테스트가 아닙니다.

보안 Advisor에는 프로젝트 전체 RLS 정책 없음 INFO 36개가 반환됐습니다. 서버 전용 비공개 테이블을 브라우저에 개방해 알림을 없애지 않았습니다. 직접 권한 확인 결과와 함께 기록했으며 전체 보안 검토 완료라고 표시하지 않습니다.

[Supabase의 RLS 정책 없음 안내](https://supabase.com/docs/guides/database/database-linter?lint=0008_rls_enabled_no_policy)

실제 DB 이력에 저장된 적용문은 34,214 bytes입니다. DB에서 계산한 Git blob SHA와 저장소에 만든 blob은 모두 `baf5a1aacd2592cb5c7af74cbb89c9bc87532409`로 일치합니다. 파일 동일성은 기능 검증과 다릅니다.

## 변경하지 않은 것

웹 화면·Edge 함수 배포, 실제 문의/답변/담당자 배정, 첫 시즌 콘텐츠 저장·승인·공개, 참가자·주문·환불 생성, Auth callback·키·서버 설정 변경, 유료 리소스 생성, 외부 알림, main 병합, 판매 활성화는 하지 않았습니다. 기존 PDF·스토어 코드·가격·일정·원고도 수정하지 않았습니다. 데이터베이스 구조와 계정 래퍼는 실제 변경됐습니다.

단위·브라우저·실로그인·결제·동시성·회귀 테스트는 실행하지 않았습니다. 수행한 확인은 설치 이력·직접 권한·일부 행 수·Advisor·SQL 파일 동일성입니다. 공개 서비스의 정상 동작 또는 판매 준비 완료를 주장하지 않습니다.
