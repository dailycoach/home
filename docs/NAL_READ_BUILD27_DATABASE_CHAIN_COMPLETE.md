이로써 구성표에 선언한 SQL 소스 19개 계층이 8개의 실제 통합 마이그레이션에 걸쳐 모두 설치됐습니다. 이는 **DB 소스 설치 완료**이며, 웹사이트 완성·API 배포·기능검증·판매 준비 100%를 의미하지 않습니다. READ 공개 모드는 OFF입니다.

## 1. 적은 계획을 작은 실험으로 이어가기

기존 실험 테이블에 `source_answer_id`, `source_snapshot`을 추가했습니다. 참가자가 저장한 TRY 답변에서 실험을 이어갈 때, 해당 본인의 기수·질문·확정 답변·수정 버전이 맞는지 확인합니다. 브라우저가 보내온 임의의 제목이나 소유자 정보로 실험을 만드는 대신 실제 저장된 원문을 참조하는 기존 설계를 설치했습니다.

같은 답변으로 다시 요청하면 기존 실험을 돌려줍니다. 이미 완료하거나 취소한 실험을 다시 시작시키거나, 나중에 바뀐 답변으로 기존 성찰을 덮어쓰지 않습니다. 초기 생성은 planned 상태이고 시작·완료는 별도입니다. 직접 작성한 다른 실험의 출처를 문장 유사도로 추정하지 않습니다.

LIVE 참여 버튼 처리도 같은 메모의 저장 잠금과 수정 버전을 함께 사용하도록 연결했습니다. 버튼을 누른 결과의 버전을 돌려주며, 다른 탭의 새 메모를 오래된 입력으로 덮어쓰는 상황을 구분하는 구조입니다. Zoom 접속 클릭은 여전히 실제 출석과 다릅니다.

위 내용은 설치된 함수 정의의 동작 설계입니다. 실제 참가자 답변이나 실험을 생성하거나 동시 수정 시나리오를 시험한 것은 아닙니다.

## 2. 운영 홈과 기수별 조회

운영 홈은 선택한 시즌의 원고 반영 상태, 안내문 편집본·공개본, 4주 진행안, 연결된 LIVE 일정, 기수·정원, 답변 대기 문의와 확인할 주문 수를 조회합니다. 원고 본문·참가자 개인 성찰·진행자 메모·Zoom 주소는 이 홈 조회에 포함하지 않습니다.

저장된 상태를 보여줄 뿐, 홈 조회로 안내문을 공개하거나 참가권을 발급하거나 결제사를 호출하지 않습니다. 미연결·권한 제한·조회 실패와 실제 빈 기록을 구분합니다. 기존 소유자·운영자 권한을 확인하고, 소유자에게만 기수·주문 집계를 제공하며 문의는 현재 배정 범위를 적용합니다.

기수별 조회는 주문·문의 목록을 서버에서 해당 시즌으로 먼저 제한한 뒤 페이지를 나눕니다. 개별 문의도 같은 기수에 속하고 현재 접근 가능한지 확인한 후 기존 문의 조회를 사용합니다. 잘못된 시즌 요청을 전체 기록 조회로 넓히지 않습니다. 문의 읽음 처리나 답변 저장은 실행하지 않습니다.

계정 RPC는 이전 구현을 보존하면서 operator-home과 operator-context를 순서대로 연결합니다. 기존 참가자 홈·계정 기능은 이전 함수로 전달합니다. 서버 기능 설정은 이후 Edge 계층에서만 주입해야 하며, 브라우저가 기능이나 역할을 바꾸도록 허용하지 않습니다.

## 3. 설치 증거와 권한

이번에 새 테이블은 만들지 않았습니다. 기존 실험 테이블에 필드 2개, 답변별 실험 중복을 막는 부분 고유 인덱스 1개, 답변 참조 외래키를 설치했습니다. 실험 테이블의 RLS와 브라우저 직접 접근 제한은 유지됐습니다.

설치 후 관찰한 함수 객체는 7개입니다. 이전 구현을 보관한 함수와 새 래퍼를 포함한 수이며, 별도 서버 7개를 배포했다는 뜻이 아닙니다. 모두 SECURITY INVOKER, 익명·로그인 브라우저 역할 실행 불가, service_role 실행 허용으로 확인했습니다.

적용문은 28,822 bytes입니다. DB 이력에서 계산한 Git blob과 저장소에 만든 blob은 `bf8044a0c9e6fceec5406fec9605000cf8a6091c`로 일치합니다. 선행 이력·계정/작업 함수 정의·READ OFF·미등록 데이터·재실행 차단 조건을 붙인 적용문이므로 옛 통합 ZIP과 동일한 바이트라고 주장하지 않습니다.

제한된 집계에서 카탈로그 31개·설정 2개·PDF 파일 메타데이터 3개를 확인했습니다. 주문·결제·참가 등록·답변·실험·운영자 멤버십·기수·문의는 0건이었습니다. 실제 데이터 행을 추가하지 않았습니다.

보안 Advisor는 이전과 같은 RLS 정책 없음 INFO 36개를 반환했습니다. 비공개 서버 전용 테이블을 브라우저에 개방하는 정책은 추가하지 않았습니다. 직접 권한 확인과 함께 기록했으며 전체 보안 검토 합격으로 표시하지 않습니다.

## 4. 다음은 DB가 아니라 실제 API·화면 연결

서버 함수 목록도 읽었습니다. 선언된 READ/account/support 함수 11개 중 이름이 존재하는 것은 `nal-read-enroll` v2와 `nal-read-daily` v3입니다. 이 둘의 현재 배포 소스가 통합본과 같은지는 아직 읽어 대조하지 않았습니다. ACTIVE 표기는 정상 동작 증거로 사용하지 않습니다.

현재 목록에 없는 함수는 nal-account, nal-read-workspace, nal-read-report, nal-read-editorial, nal-read-cohorts, nal-read-companion, nal-support, nal-read-payments, nal-read-payments-webhook의 9개입니다. 기존 PDF 다운로드·PDF 결제·webhook·일회성 원본 업로드 함수는 변경하지 않았습니다.

따라서 남은 일은 더 많은 DB 계층을 만드는 것이 아니라, 기존 두 함수의 소스를 확인하고 필요한 9개와 함께 공유 인증 모듈·의존 파일을 맞춰 배포한 뒤, 프런트엔드와 실제 연결 설정을 붙이는 것입니다. 이번 BUILD27에서는 API나 화면 배포를 하지 않았습니다.

기수·원고·진행안·모집 일정·정원·운영자 계정 권한은 아직 자동 입력하지 않았습니다. 고객 판매 모드, 개인정보 보관·삭제 동작과 판매 전 사용자 흐름 검증도 별도입니다. 특히 답변 외래키의 ON DELETE SET NULL은 참조만 끊으며 출처 사본이나 리포트 사본의 텍스트를 지우지 않습니다. 이것을 삭제 기능 완료로 해석하지 않습니다.
