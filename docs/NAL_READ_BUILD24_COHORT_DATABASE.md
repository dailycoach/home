# NAL READ BUILD24 — 기수·정원·대기·참가자 DB 연결

## 실제 적용

기존 nal-platform에 BUILD09 COHORTS, COHORT_ADMIN, ADMISSION_BRIDGES 세 계층을 한 마이그레이션으로 적용했습니다. 성공 응답과 실제 이력에서 확인한 버전은 `20261007150710 / nal_read_build24_cohort_admission_integration`입니다. 누적 DB 적용은 19개 중 11개이며, 8개가 남습니다. 서비스 전체 완성률을 뜻하는 숫자가 아닙니다.

기준 소스는 `3ccdbe665435734e5eb6f40922b49ddf9d8ff54e`입니다. 첫 여덟 계층은 다시 실행하지 않았습니다. 기존 통합 잠금, 실제 선행 이력 확인, READ OFF, 신규 기수 구조 미존재, 주문·참가 등록 미존재 조건을 붙인 후속 변경분만 적용했습니다. 실제 적용문의 SQL을 반환된 이력 버전으로 저장소에 보관합니다.

## 이번에 연결한 운영 구조

| 저장 구조 | 역할 |
| --- | --- |
| read_cohorts | 프로그램 묶음·기수 번호·이름·일정·정원·모집 상태 |
| read_waitlist | 대기 신청 순서·참여 기회 기한·철회·참가 전환 |
| read_cohort_attendance | 실제 모임에 대한 운영자 확인 출석 |
| read_cohort_events | 설정·제안·철회·출석 변경 이력 |

한 시즌은 한 운영 기수이며, program_key가 여러 기수를 같은 정규 상품군으로 묶습니다. 여기에는 실제 기수 이름·일정·정원이나 참가자를 삽입하지 않았습니다.

정원 계산은 참가 등록, 유효하거나 확인 중인 주문, 기한이 남은 대기자 제안을 합치되 같은 사용자를 중복 계산하지 않습니다. 단순 대기 신청과 실제 확보된 자리는 구분합니다. 결제 결과가 불명확한 주문을 임의로 지워 자리를 다시 판매하지 않는 기존 설계를 연결했습니다.

대기 순서는 신청 시각과 사용자 식별자의 안정적인 순서로 정합니다. 같은 신청을 다시 보내도 기존 순서를 초기화하지 않으며, 소유자가 앞 순서의 대기자에게 기한이 있는 참여 기회를 명시적으로 제안하는 구조입니다. 제안·철회는 자동 결제나 환불이 아닙니다. 문자·메일 알림은 추가하지 않았습니다.

참가자 명단은 표시 이름·참가 상태·기록한 DAY 수·출석을 위한 기존 조회에 연결됩니다. 개인 질문 답변·실험 성찰·심리점수나 Auth 계정 전체 정보를 가져오는 구조를 추가하지 않았습니다. 출석 기록은 시작된 공개 LIVE와 해당 기수 참가자가 일치해야 하며, Zoom 접속 클릭과 별도입니다. 출석 변경은 기존 소유자 권한으로 명시적으로 기록합니다.

## 화면뿐 아니라 실제 발급 경로에 정원 연결

참가권 발급, 가입, 주문 생성과 결제 재개, 결제 결과 처리, 참가권 전달, 상품 조회·설정의 기존 함수 앞에 기수 확인을 연결했습니다. 기존 신원·소유권·결제 확인·공개 범위 함수는 보존하고 그 바깥에 정원 검사를 추가했습니다.

주문 삽입 전 정원 확인, 참가 등록 전 정원 확인, 등록 후 기존 대기 신청을 참가 상태로 바꾸는 트리거 3개를 설치했습니다. 따라서 참가 화면에만 정원 안내를 붙인 단계가 아닙니다. 그렇다고 실제 초과신청·동시결제 시나리오를 시험한 것도 아닙니다. 이번에는 함수와 트리거 정의만 설치했습니다.

신청 기록이 생긴 기수의 일정·이름 등을 조용히 바꾸지 못하게 하고, 이미 확보된 자리 수보다 정원을 낮추지 못하도록 기존 설정 함수를 연결했습니다. 기존 참가자의 기록을 다른 기수로 옮기는 수정도 제한합니다. 취소 상태 변경은 실제 금전 환불과 분리됩니다.

## 설치 후 관찰 범위

새 테이블 4개는 모두 RLS를 사용하며 익명·로그인 브라우저 역할의 직접 권한은 없습니다. 신규 및 기존 이름을 옮겨 연결한 함수 24개를 조회했고, 모두 SECURITY INVOKER이며 브라우저 역할 실행 권한이 없었습니다. 이 중 21개는 서버 실행 권한이 있고, 트리거 전용 함수 3개에는 직접 서버 실행 권한을 부여하지 않았습니다. 24개는 모두 새 기능을 만든 개수가 아니라 보존된 내부 함수 7개까지 포함한 관찰 대상 수입니다.

READ 공개는 OFF였습니다. 기수·대기·출석·기수 변경 이력은 모두 0행이며, 실제 주문·결제·READ 참가 등록·답변·운영자 멤버십도 0으로 확인했습니다. 카탈로그 31개, 설정 2개, PDF 파일 메타데이터 3개는 이전 확인 수와 같습니다. 이 수치는 제한된 집계이며 전수 데이터 동일성 검사를 의미하지 않습니다.

보안 Advisor에서는 프로젝트 전체에 `rls_enabled_no_policy` INFO 29개가 반환됐습니다. 서버 전용 비공개 테이블을 브라우저에 개방하는 정책은 추가하지 않았습니다. 실제 직접 권한 조회와 함께 해석했으며, 전체 보안 검토 합격으로 표시하지 않습니다.

참고 안내: https://supabase.com/docs/guides/database/database-linter?lint=0008_rls_enabled_no_policy

## 실행하지 않은 것

Edge 함수나 웹 화면 배포, 고객 판매·결제 활성화, 운영자 권한 부여, 첫 기수 입력, 실제 또는 샘플 참가자·주문·출석 생성, 외부 메시지·결제사 요청, main 병합은 하지 않았습니다. 새 유료 리소스도 만들지 않았습니다. 기존 무료 PDF·원고·카탈로그 가격·모집 일정·Auth 설정은 변경하지 않았습니다. 데이터베이스의 함수·테이블·트리거는 실제 변경됐습니다.

단위·브라우저·로그인·결제·동시성·회귀 테스트는 실행하지 않았습니다. 설치 이력·권한·일부 행 수와 Advisor 조회만 수행했습니다. 고객 판매 직전의 기능 검증은 별도로 남아 있습니다.

## 재개 기준

`integration/nal-read/build24/resume-plan.json`이 이번 적용 이후의 새 기준입니다. 이전 BUILD22 문서에 미적용으로 적힌 결제·기수 부분은 이제 실제 이력상 설치된 계층입니다. 과거 문서를 정상 상태로 위조하거나, 차단됐던 BUILD23 문서 쓰기를 다른 경로로 재시도하지 않았습니다.

다음은 BUILD10의 참가자 시작 안내·진행자 스튜디오·기존 첫 화면 연결입니다. 이후 문의, 참가자 홈, 질문-실험 연결, 운영 홈, 기수별 조회의 순서로 남은 여덟 계층을 이어갑니다. 완성된 19개 전체 후보를 처음부터 재실행하거나 전체 완료 마커를 기록하면 안 됩니다. 현재 기능에 맞춘 DB·API·화면 통합과 판매 전 검증은 아직 끝나지 않았습니다.

공식 Supabase 문서 검색으로 스키마 및 실행 권한 설명을 확인했습니다. changelog.md 요청은 지원하지 않는 content-type으로 반환되어 최신 SDK 동작을 추정하지 않았습니다. SDK·CLI를 설치하거나 변경하지 않았고, 마이그레이션 파일명은 실제 적용 이력에서 반환된 식별자를 사용했습니다.
