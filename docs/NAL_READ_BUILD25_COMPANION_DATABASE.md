# NAL READ BUILD25 — 시작 안내·진행자 스튜디오 DB 실제 연결

## 완료한 두 가지

먼저 지난 BUILD24의 GitHub 브랜치 연결 오류를 해결했습니다. 실제 브랜치를 다시 읽은 뒤, 기대한 이전 HEAD를 조건으로 강제 갱신 없이 `035c92d0ee4d8fd1d0a160d56de49c5c93601b59`를 `feat/nal-read-v1`에 연결했습니다. 이후 ref 조회에서도 같은 커밋을 확인했습니다. 이미 성공했던 기수 DB는 다시 적용하지 않았습니다.

이어서 BUILD10 GUIDE·STUDIO·ARRIVAL_BRIDGE 세 계층을 기존 nal-platform에 실제 적용했습니다. 반환된 적용 이력은 `20261007210247 / nal_read_build25_companion_studio_integration`입니다. 누적 SQL 소스 계층은 19개 중 14개이며, 플랫폼 전체 완성률이나 기능검증 점수가 아닙니다.

설치 확인 시각은 2026-10-07 21:03:18 UTC, 한국 시간으로 2026년 10월 8일 06:03:18입니다. 마이그레이션 파일명은 실제 이력의 UTC 기반 식별자를 그대로 사용했습니다.

## 참가자 안내와 개인 준비

`read_arrival_guides`에는 소개·참여 대상·가져갈 것·독서 안내·시작 전 안내·도서 정보·준비 항목·FAQ를 저장합니다. 편집본과 공개본을 분리합니다. 원고를 고쳐 저장해도 이전 공개본은 그대로 남으며, 소유자의 명시적 공개 동작으로만 교체됩니다.

`read_preparation_checks`에는 현재 공개 안내에 포함된 항목에 대한 참가자 자신의 준비 확인을 저장합니다. 임의의 키나 다른 버전의 안내에 대한 체크를 저장하지 않으며, 동시 수정은 버전 충돌로 구분합니다. 준비 확인은 책을 읽었다는 인증·DAY 완료·LIVE 출석·다음 질문 해제와 다릅니다.

시작 전·진행 중·운영 종료·일정 미정·취소 상태를 구분하는 DB 조회를 연결했습니다. 공개 소개에는 승인된 안내문과 공개 일정 메타데이터만 포함하고, 초안·진행자 내부 메모·개인 성찰·Zoom 접속 주소를 섞지 않습니다. 실제 페이지/API 배포는 이번 범위가 아닙니다.

## 진행자 스튜디오와 변경 이력

`read_facilitator_plans`는 기수의 1~4주차 진행안을 저장합니다. 목적·시작과 마무리 문장·후속 안내·순서별 질문과 시간 배분·내부 진행 메모·운영 회고를 다룹니다. 실제 연결할 LIVE는 같은 시즌과 주차에 속해야 합니다. 초안과 작성 완료를 구분하며, 작성 완료가 실제 개최나 출석 확인이라는 뜻은 아닙니다.

운영자는 해당 주차의 공개된 교육 콘텐츠를 참고할 수 있지만 참가자의 답변·초안·실험 성찰·개인 LIVE 메모를 조회하는 기능은 추가하지 않았습니다. 안내문과 진행안의 변경 기록은 `read_companion_history`에 별도로 남기는 기존 소스 구조를 설치했습니다.

이 네 테이블에 실제 안내·진행안·준비 체크를 입력하지 않았습니다. 첫 시즌 원고를 새로 쓰거나 승인·공개한 작업도 아닙니다.

## 첫 화면과의 연결

기존 `nal_read_bootstrap` 구현을 비공개 `read_bootstrap_before_arrival`로 보존하고, 원래 결과에 시작 안내 상태를 더하는 새 래퍼를 설치했습니다. 기존 DAY 공개와 소유권 판단을 재작성하지 않았습니다. 새 조회 자체로 질문을 시작하거나 학습 기록을 완료하지 않습니다.

이번에 관찰한 함수 객체는 8개이며, 보존된 이전 bootstrap 1개를 포함합니다. 새 Edge Function 8개를 배포했다는 뜻이 아닙니다.

## 실제 적용과 확인 범위

세 계층은 하나의 트랜잭션으로 적용했습니다. 선행 BUILD22~24 실제 이력, PostgreSQL 17, READ OFF, 기존 bootstrap/access 정의, 새 구조 미존재, 주문·참가자 미등록 조건을 확인하는 후속 변경분입니다. 과거 19개 전체 SQL에서 조건을 제거해 재실행하지 않았습니다.

설치 후 새 테이블 4개는 모두 RLS를 사용하며 익명·로그인 브라우저 역할의 직접 권한이 없습니다. 조회한 함수 8개는 SECURITY INVOKER이며 브라우저 역할의 직접 실행 권한 없이 서버 역할에만 실행을 허용합니다. READ 공개 모드는 OFF였습니다.

제한된 집계에서 카탈로그 31개·설정 2개·기존 PDF 파일 메타데이터 3개를 확인했습니다. 주문·READ 등록·답변·운영자 멤버십·기수와 새 안내·준비 체크·이력·진행안은 0건이었습니다. 이는 설치 경계 확인이지 전수 데이터 동일성 검사가 아닙니다.

보안 Advisor는 프로젝트 전체에 RLS 정책 없음 INFO 33개를 반환했습니다. 서버 전용 테이블을 브라우저에 개방하는 정책을 추가하지 않았습니다. 직접 권한 확인과 함께 기록했으며, 전반적인 보안 검토 합격으로 표시하지 않습니다.

[Supabase의 해당 안내](https://supabase.com/docs/guides/database/database-linter?lint=0008_rls_enabled_no_policy)

적용문은 29,087 bytes이며, 실제 DB 이력에서 계산한 Git blob SHA와 저장소에 만든 blob은 모두 `328ee890191457b689c1dd5cf0d5d47b564bd08b`입니다. 파일 동일성 확인은 기능 테스트가 아닙니다.

## 변경하지 않은 것과 다음 범위

Edge/API·프런트엔드 배포, Auth callback·키·환경 설정, 권한 부여, 참가자나 샘플 기록, 실제 일정·정원, 결제사 호출·환불, 외부 알림, main 병합, 고객 판매 활성화는 수행하지 않았습니다. 무료 PDF·기존 스토어 코드·가격·첫 시즌 원고는 수정하지 않았고 새 유료 리소스도 만들지 않았습니다.

단위·브라우저·실로그인·결제·동시성·회귀 테스트는 수행하지 않았습니다. 실행한 확인은 설치 이력·직접 권한·일부 건수·Advisor·SQL 동일성입니다.

새 재개 기준은 `integration/nal-read/build25/resume-plan.json`입니다. 남은 다섯 계층은 문의 → 참가자 홈 → 질문·실험 연결 → 운영 홈 → 기수별 조회입니다. 현재 DB는 14개가 설치된 부분 통합 상태이며, 과거 깨끗한 기반용 SQL을 다시 실행하거나 전체 완료 마커를 추가하지 않습니다. 고객 화면을 여는 단계는 필요한 DB·API·화면이 함께 연결된 뒤 별도로 진행합니다.
