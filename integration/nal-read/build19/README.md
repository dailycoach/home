# NAL READ · BUILD19 통합 구성

## 이번 결과

여러 BUILD에 나누어 작성한 소스를 같은 기준 버전에서 모으는 **오프라인 패키지 생성기와 적용 구성표**입니다. 앱 기능을 다시 만들거나 운영 서버에 적용하지 않았습니다. 패키지 생성기 자체도 이번 작성 단계에서는 실행하지 않았습니다.

앱 기준 커밋은 `0e2e8652212748278067c2981502174a6c109c18`입니다. BUILD19는 그 위에 도구·구성·안내 파일만 추가합니다. 나중에 브랜치에 다른 코드가 더해져도 이 패키지가 몰래 그 코드를 섞어 가져오지는 않습니다. 최신 앱을 묶으려면 기준 커밋·구성표를 명시적으로 갱신해야 합니다.

## 구성 파일

| 파일 | 역할 |
| --- | --- |
| `manifest.json` | 고정 커밋, 기존 기반 참조, DB 추가 적용분 19개와 선행 순서, 포함·제외할 소스 |
| `runtime-plan.json` | 11개 서버 함수와 화면·DB의 대응, 기존 플랫폼 의존성, 아직 확정하지 않은 연결 항목 |
| `target-evidence.template.json` | 나중에 대상 서버·실제 적용 이력을 확인할 때 기록하는 빈 양식. 실행 설정이 아님 |
| `scripts/package-nal-read-build19.py` | 로컬 Git 객체에서 원본을 모으고 ZIP·파일 목록·해시를 생성하는 도구 |

## 패키지 생성 방법 — 실행은 별도

로컬에 저장소와 BUILD19 커밋이 이미 있고 Python 3.10 이상과 Git이 설치된 환경에서 사용합니다. `pip install`, 새 서버, 유료 SDK가 필요하지 않은 표준 라이브러리 방식으로 작성했습니다. 이 명령은 **DB 적용이나 배포 명령이 아닙니다.**

저장소 루트에서:

```sh
python scripts/package-nal-read-build19.py --out ../nal-read-build19-source
```

출력 폴더는 저장소 밖의 새 폴더여야 합니다. 상위 폴더는 있어야 하고, 같은 이름의 기존 폴더를 덮어쓰지 않습니다. 성공하면 ZIP, ZIP의 SHA-256 파일, `SUMMARY.json`을 만들도록 작성했습니다. 중간에 실패한 출력에는 `INCOMPLETE.txt`를 남기므로 완성본으로 사용하지 않습니다.

생성기는 로컬 Git에 기준 커밋이 없으면 중단합니다. 저장소를 복제하거나 누락된 Git/LFS 객체를 네트워크로 가져오는 기능은 없습니다. 현재 작업 폴더의 수정 파일이나 `.env`, 실제 연결 JSON, 비밀번호·키 파일을 포괄적으로 복사하지 않습니다. 앱 원본과 도구 원본은 각각 기록된 커밋에서 읽습니다.

## 생성되도록 작성한 패키지 구조

```text
START-HERE.md
PACKAGE.json                       # 소스/도구 기준 커밋과 수행 범위
FILE-INVENTORY.json                # 파일별 원래 경로·Git blob·SHA-256
DATABASE-PLAN.json                 # 19개 추가 SQL의 순서·의존성; 실행기 아님
RUNTIME-PLAN.json                  # 서버 함수·화면·운영 연결 구성
CHECKSUMS.sha256                   # 자기 자신을 제외한 파일 해시
reference/baseline/                # 기존 기반 마이그레이션: 재실행 목록이 아님
sql/sequence/01-...sql             # 추가 SQL 원문, 개별 BEGIN/COMMIT 유지
source/nal/...                     # READ·MY NAL·운영 화면 소스
source/supabase/functions/...       # 서버 함수·공유 모듈 소스
source/content/nal-read/...         # 첫 시즌 원고 입력 자료
package-tools/...                  # 생성기·구성표·안내 원본
templates/backend.disabled.json    # enabled=false, 연결 주소·키는 빈 값
templates/target-evidence.json     # 확인되지 않은 상태는 null/unknown
```

파일 순서, ZIP 내부 시각과 권한 표기를 고정하고 압축을 사용하지 않아 같은 소스·도구 입력에서 같은 바이트를 생성하도록 작성했습니다. 이 성질도 아직 실행해 검증한 것은 아닙니다. 해시는 파일 동일성 정보이지 기능·보안·DB 정상 동작의 검사 결과가 아닙니다.

## DB: 기반과 추가 적용분을 섞지 않습니다

기본 구성은 **FIX03 기반을 실제로 확인한 뒤, BUILD04 이전 상태에서 추가 소스를 통합하는 경우**를 설명합니다. 현재 어느 서버가 이 상태인지 확인한 것은 아닙니다.

기반 참조에는 STORE·결제·READ의 기존 마이그레이션을 넣습니다. 참조 파일이 있다는 이유로 다시 실행하면 안 됩니다. FIX02 기록 마이그레이션 안에는 수정된 FIX01과 공개 범위 제어가 함께 들어 있습니다. FIX01 초안, FIX02 부품, FIX03 사본을 각각 더 실행하는 순서를 만들지 않았습니다.

추가 SQL은 다음 순서입니다.

```text
04 WORKSPACE
  → 05 EDITORIAL → 05 REPORT
  → 06 JOIN → 06 ACCOUNT
  → 07 PAYMENTS → 07 RECONCILIATION → 07 INTEGRATION
  → 09 COHORTS → 09 COHORT ADMIN → 09 ADMISSION BRIDGES
  → 10 GUIDE → 10 STUDIO → 10 ARRIVAL BRIDGE
  → 12 SUPPORT
  → 14 HOME
  → 15 PATHWAY
  → 17 OPERATIONS
  → 18 CONTEXT
```

이 19개는 Git에서 작성된 원문이며 대상 DB의 실제 적용 여부는 모두 `unknown`으로 기록합니다. BUILD08·11·13·16은 독립 SQL 단계가 없고 해당 버전의 화면·함수·콘텐츠로 반영됩니다.

이미 일부가 적용된 서버, 수동 SQL이 적용된 서버, 완전히 빈 서버에는 이 순서를 그대로 재실행하지 않습니다. 특히 여러 파일이 기존 함수를 다른 이름으로 옮기는 연결 코드를 포함하므로 임의의 재실행이나 중간 누락을 안전하다고 가정하지 않습니다. 실제 이력과 스키마를 확인한 후 필요한 전진 변경분을 별도 마이그레이션으로 만들어야 합니다. 생성기는 실행용 `apply.sql`, DB 연결 명령, 이력 보정 명령을 만들지 않습니다.

## API와 화면: 같은 버전끼리 묶습니다

계정·참가자·원고 편집·기수·시작 안내/진행안·문의·READ 결제의 7개 기능 묶음에 11개 서버 함수가 연결됩니다. 각각 필요한 SQL과 화면 파일은 `runtime-plan.json`에 나누어 적었습니다.

새 계정이나 인증 우회는 만들지 않습니다. 실제 연결 주소, 공개 클라이언트 키, 서버 전용 키, 허용 Origin, Auth callback, 결제사 설정은 이 패키지의 소스 자료와 별도입니다. 연결 계획의 `false` 값은 초기 통합용 제안값이지 현재 서버 값을 조회한 결과가 아닙니다. 기존 운영 환경에 그대로 덮어쓰면 안 됩니다.

고객용 GET, 로그인 사용자 POST, 외부 결제사 webhook은 인증 방식이 다릅니다. gateway의 JWT 설정을 전역으로 끄거나 서버 함수마다 무조건 같은 설정을 적용하지 않습니다. 기존 검증·사용자 소유권·운영자 배정 권한은 유지합니다.

기존 PDF webhook의 READ 주문 제외 처리도 참조로 포함합니다. **해당 handler 한 파일만 별도로 배포하거나 기존 PDF receiver를 지우면 안 됩니다.** 무료 PDF와 기존 스토어는 계속 별도 경계를 유지합니다.

## 프런트엔드와 원고의 범위

이 패키지는 완성된 정적 사이트 ZIP이 아닙니다. 기존 NAL 공통 스타일·테마는 참조하지만 기존 이미지·폰트·무료 PDF·스토어 전체 카탈로그를 새 패키지에 복제하지 않습니다. 기존 호스트 자산은 보존해야 합니다. 실제 backend JSON도 포함하지 않습니다. 앱의 이전 직접 진입 HTML과 동적 로더의 캐시 버전은 원문 그대로 보관하므로 실제 통합 전에 함께 정렬해야 합니다.

서버 소스와 SQL이 함께 들어 있으므로 **ZIP 전체를 공개 웹사이트 폴더에 업로드하지 않습니다.** 배포용 디렉터리와 비공개 서버/DB 소스는 분리해서 다뤄야 합니다.

DAY 원고, 참가자 소개·준비 안내, 4주 진행안은 편집 입력으로 묶습니다. 패키지를 만들거나 원고를 불러왔다고 저장·승인·공개하지 않습니다. 실제 기수 날짜·정원·카탈로그 연결·최종 이용 조건도 자동 생성하지 않습니다.

## 이번 단계에서 하지 않은 것

패키지 생성기 실행, 테스트·화면 검증, DB 조회/적용, 새 서버 함수 배포, 실로그인·문의·결제, 권한 변경, 운영 설정 변경, 첫 기수 데이터 생성, main 병합, 고객 판매 활성화는 하지 않았습니다. 구성 파일의 `unknown`과 `null`을 정상·0건·미적용으로 해석하지 않습니다.

다음 통합 작업은 대상 환경의 기존 기반을 확인하고, 필요한 DB 전진 변경과 함께 적용할 API·화면 파일을 확정하는 것입니다. 고객 판매 직전 검증은 별도 단계로 남겨둡니다. 현재 소스의 OFF/test_only 제어를 정상 고객 판매 모드로 바꾸는 작업도 이 패키지에 포함하지 않습니다.
